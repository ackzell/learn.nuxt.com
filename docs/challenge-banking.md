# Challenge Banking

Checkable challenges are **authored once** in a shared bank and **referenced by
lesson**. A lesson's `.template/index.ts` sets `validation.challenge` to the
bank id; at build time the mounted `__challenge__/suite.<ext>` is generated
from the bank with the lesson locale's display strings baked in. The runtime
side of this flow (how the suite executes inside the preview iframe) is
covered in [`docs/preview-system.md`](preview-system.md) ->
"Challenge Validation Suites".

---

## The model

```text
lessons reference a bank by id          bank authoring lives here
──────────────────────────────          ──────────────────────────
content/en/04.../04b.challenge/        challenges/conditional-challenge/
  index.md                                suite.ts      (the only checks)
  .template/index.ts                     en.yaml       (strings)
  .template/files/src/App.vue      →     es_mx.yaml     (strings)
  .template/solutions/src/App.vue

build (template-loader transform)
  reads challenges/conditional-challenge/suite.ts
  bakes en/es checks names + hints into the suite
  rewrites the `harness` import to the relative runtime path
  injects the result as __challenge__/suite.ts in the mounted files
```

- **One bank, many lessons.** The same bank id can be referenced by any number
  of lessons (e.g. the `en` and `es_mx` mirrors). The checks live in exactly
  one place; the mounted file is generated per lesson at build time.
- **The suite path is derived from the lesson's `template`, never authored**
  (`getChallengeSuiteFile` in `types/guides.ts`):

  | Template   | Mounted suite file        |
  | ---------- | ------------------------- |
  | `html`     | `/__challenge__/suite.js` |
  | `vue`      | `/__challenge__/suite.ts` |
  | `vue-sass` | `/__challenge__/suite.ts` |

## Bank layout

```text
challenges/<id>/
  suite.ts      canonical suite (legacy `.js` banks still supported)
  en.yaml       display strings, keyed by check id
  es_mx.yaml    display strings, keyed by check id
```

The skeleton for a new bank is generated by the `content` CLI (see
[Scaffolding with the CLI](#scaffolding-with-the-cli)) — or copy an existing
bank, e.g. `challenges/basics-challenge/`.

### Authoring environment

Bank suites are written in TypeScript with full intellisense:

- `challenges/__shared__/harness.d.ts` — the typed authoring surface
  (`check`, `checks`, `expect`, `ChecksOptions`, `CheckContext`,
  `DomWrapperLike`, `describe`/`it`/`test`, `startChallengeRuntime`, …).
- `challenges/__shared__/shims.d.ts` — ambient module types for
  `*.vue` and `*.vue?raw` imports from inside a bank suite.
- `challenges/tsconfig.json` — maps the bare `harness` import to the shared
  declarations (`paths: { "harness": ["./__shared__/harness.d.ts"] }`).
- The root `tsconfig.json` **excludes** `challenges/` so the Nuxt aliases
  (`~`, `@`) are unaffected.

Verify a bank at authoring time:

```bash
npx tsc --noEmit -p challenges/tsconfig.json
```

## Authoring a suite

Import the DSL from the bare `harness` module (the build rewrites the import
to the correct relative runtime path per template — authors never write it):

```ts
import { check, checks, expect } from 'harness'

export default checks([
  // check('<id>', { ... }) — entries go here
])
```

- `check('<id>', spec)` — the **first argument is the check id**, used as the
  key in `<locale>.yaml` to resolve the localized display name and hint at
  build time. It must match a `checks.<id>` entry in the strings (see
  [Localizing checks](#localizing-checks)).
- `checks([...])` wraps the list and marks the module as a suite.
- `expect(value).toX()`, `expect(value).not.toX()` — hand-rolled vitest-style
  matchers (`toBe`, `toEqual`, `toContain`, `toMatch`, `toBeTruthy`,
  `toBeGreaterThan`, …). They work identically in the dependency-free `html`
  harness and the Vue Test Utils backed Vue harness.
- `describe` / `it` / `test` — minimal shims for migrating existing suites.
  The empty-suite rule ("add at least one check() or it()") applies here too.

### The check context

Every check's `run` receives a context:

- `{ doc }` — the live `document` inside the preview iframe (same origin).
  Available in every template.
- `{ mount }` — Vue Test Utils `mount`, only for `vue` / `vue-sass`
  templates. Returns a VTU wrapper typed as `DomWrapperLike`
  (`exists`, `find`, `findAll`, `text`, `html`, `classes`) so authoring stays
  type-narrowed without pulling the VTU dependency into the bank.
- `ChecksOptions.setup(ctx)` may return partial overrides injected into the
  context for every check.

Example (DOM assertions):

```ts
check('renders-current-branch', {
  run({ doc }) {
    expect(doc.querySelector('.msg-mid')?.textContent).toContain('Getting there')
  },
})
```

Example (Vue Test Utils mount):

```ts
import App from '../src/App.vue'

check('renders-current-branch', {
  run({ mount }) {
    const wrapper = mount(App)
    expect(wrapper.find('.msg-new').exists()).toBe(false)
    expect(wrapper.find('.msg-mid').exists()).toBe(true)
  },
})
```

### Source-inspection checks

For `vue` / `vue-sass`, checks can also assert against the learner's **source**
via Vite's `?raw` import. This is the idiomatic way to verify a directive is
used (e.g. a challenge about `v-if` / `v-else-if` / `v-else`):

```ts
import AppSource from '../src/App.vue?raw'

check('uses-v-if', {
  run() {
    expect(AppSource).toMatch(/v-if[\s=]/)
  },
})
```

Because the suite lives in `__challenge__/` next to the learner's files, both
`'../src/App.vue'` and `'../src/App.vue?raw'` resolve at runtime inside the
container's dev server.

## Localizing checks

`en.yaml` / `es_mx.yaml` are keyed by the bank id, then by check id. The yaml
`name` becomes the displayed check name and `hint` the failure hint:

```yaml
conditional-challenge:
  checks:
    uses-v-if:
      name: Uses v-if
      hint: Expected the v-if directive to be used in App.vue
    renders-current-branch:
      name: Shows only the matching branch
      hint: Expected only the branch matching the current level to be shown
```

- The build resolves strings for the lesson's locale
  (from the lesson path under `content/<locale>/...`) with `en` as fallback;
  a check with no string entry displays its raw id.
- `validateChallengeStrings` (`lib/challenge-validation.ts`) warns (at build)
  when a check id has no string entry, when yaml defines an id the suite does
  not use, or when the suite authors an inline `hint:` (hints belong in yaml).
  It does **not** throw — partial translations degrade to raw ids.

## Lesson wiring

A challenge lesson references the bank in `.template/index.ts`:

```ts
import type { GuideMeta } from '~/types/guides'

export const meta: GuideMeta = {
  template: 'vue',
  startingFile: 'src/App.vue',
  sessionName: 'conditional-challenge',
  validation: {
    challenge: 'conditional-challenge',
  },
}
```

- `sessionName` is the shared progress key — the `en` and `es_mx` mirrors use
  the **same** value so completing one marks the other.
- `isChallenge: true` frontmatter in `index.md` plus the presence of the
  `validation` block auto-inject the `::challenge` / `::challenge-check` UI.
- Starter files go under `.template/files/`, reference solutions under
  `.template/solutions/` (the solution overlay swaps `files/` for
  `solutions/`).

## Build-time bake

`modules/template-loader.ts` runs a transform over every `.template/index.ts`.
When the meta declares `validation.challenge`, it calls
`generateChallengeSuiteFile` (`lib/challenge-banking.ts`), which:

1. resolves the mounted path from the lesson's `template`;
2. reads `challenges/<id>/suite.ts` (falling back to `suite.js` for legacy
   banks) and registers it (plus the locale yaml) as a transform watch file;
3. transpiles `.ts` → `.js` for **html** mounts (the static server has no
   build step) — the Vue templates keep `.ts` (Vite transpiles at runtime);
4. bakes in the localized check names/hints (`bakeSuite`);
5. rewrites the bare `harness` import to `./harness` (Vue) or `./harness.js`
   (html) (`normalizeHarnessImport`);
6. injects the result into `meta.files` as `__challenge__/suite.<ext>`, so the
   mounted suite is always generated — never a per-locale authored file.

## Runtime execution

Runtime details live in `docs/preview-system.md` -> "Challenge Validation
Suites"; in short:

- **html** (static): the reserved `?challenge=` query param makes the static
  server inject the harness script; the suite is plain `.js`.
- **vue / vue-sass**: `src/main.ts` lazily imports the harness on the first
  challenge postMessage; the host derives the suite path via
  `getChallengeSuiteFile(template)` and sends it in the `run-suite` message
  `file` field. The harness unwraps the ESM `.default` namespace, so
  `export default checks([...])` works.
- Results travel back over the same `suite-result` postMessage protocol (with
  the echoed request id); **empty suites fail explicitly**; a passing suite is
  recorded in `db/challenges` under the lesson's `sessionName`.

## Debugging

Set `window.__challengeDebug = true` in the browser console before interacting
with a challenge to enable the `[challenge-debug]` logs (host-side: check
button, suite bridge, validation outcomes, IndexedDB writes). Full probe list:
`docs/preview-system.md` -> "Debugging the challenge flow".

## Scaffolding with the CLI

The `content` CLI (`packages/create-content`) scaffolds challenge lessons
bank-first:

```bash
content lesson      # answer "Make this a checkable challenge?" → yes
```

It prompts for a **bank id** (defaults to the lesson slug) and then:

- writes `validation: { challenge: '<bank-id>' }` into the lesson's
  `.template/index.ts` (the suite path itself is never authored);
- creates `challenges/<bank-id>/` once: `suite.ts` (bare `harness` import, an
  explicit failing TODO check so a fresh bank never passes an empty suite)
  plus `en.yaml` / `es_mx.yaml` stubs keyed by the TODO check id;
- scaffolds `.template/files/` starters and `.template/solutions/`.

The bank is written idempotently — creating the mirror lesson in a second
locale reuses the existing bank.
